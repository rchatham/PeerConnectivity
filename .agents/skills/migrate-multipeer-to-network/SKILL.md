# Migrate MultipeerConnectivity to Network.framework

Use this skill when changing an app that adopts PeerConnectivity. The Network backend is experimental and opt-in; MultipeerConnectivity (MC) remains the default. This workflow does not authorize changing the library default or removing MC.

## Ordered reading

Read these files in order before proposing changes:

1. `MultipeerConnectivityToNetworkMigrationGuide.md` — adopter workflow and rollout contract.
2. `NetworkBackendGuide.md` — current API behavior, setup, support matrix, and device caveats.
3. `NetworkMigrationReadinessAudit.md` — authoritative stable/default/removal gates.
4. `NetworkTrustModelPlan.md` — current PSK trust boundary and identity risks.
5. The adopting app's manager construction, event listeners, browser/invitation UI, messages, `Info.plist`, deployment targets, tests, and release controls.
6. `PeerConnectivityDemo/README.md` when a runnable dual-backend example is useful.

Read `NetworkFrameworkMigrationPlan.md` and `NetworkMigrationPRPlan.md` only when implementation history or architecture sequencing is relevant.

## Discovery questions

Answer these from the app and confirm unknown product requirements with the user:

1. Which platforms, minimum OS versions, physical devices, and network topologies must work?
2. Which `serviceType` values exist, and which app targets declare their Bonjour types?
3. Does the app use reliable `Data`/`PeerMessage`, streams, resources, `multipeerSession`, certificate events, or legacy dictionary events?
4. Does it use `.automatic`, `.inviteOnly`, `.custom`, `MCBrowserViewController`, invitation context/timeouts, or inbound approval?
5. Does authorization, audit, or safety logic trust a display name or peer identifier?
6. How will a 32+-byte random PSK be provisioned, stored, scoped, rotated, and revoked?
7. Which app/protocol versions must interoperate, and how will all participants select the same backend?
8. What observability, staged rollout, rollback threshold, and rollback owner exist?
9. What physical-device matrix and Local Network allow/deny/recovery UX will be release-gated?

If answers reveal MC-only APIs, individual identity requirements, or mandatory inbound approval, keep MC for that path unless a separately scoped and reviewed replacement is accepted.

## Phased workflow

### Phase 1: inventory and classify

- Locate every `PeerConnectionManager` initializer and record backend, connection type, security, discovery info, and invitation policy.
- Locate stream/resource/session/certificate APIs and exhaustive `PeerConnectionEvent` switches.
- Map bare service names to `_service._tcp` and inspect the adopting app target's built plist inputs.
- Document application message versions, identity assumptions, peer-selection UX, topology, and lifecycle behavior.
- Classify each feature as Network-supported, app replacement required, MC-only, or blocked.

### Phase 2: design the migration seam

- Keep `.multipeerConnectivity` as the safe default/fallback.
- Add an app-owned backend selection seam; do not add a transport bridge.
- Require all expected peers in a session to select the same backend.
- Plan mixed-version cohorting and explicit app-message compatibility.
- Define metrics, rollout cohorts, rollback thresholds, and ownership before enabling Network.

### Phase 3: configure the app target

- Confirm iOS 13.0+/macOS 10.15+ and availability behavior.
- Validate each bare service type with `PeerConnectionManager.isValidServiceType(_:)`.
- Add `NSLocalNetworkUsageDescription` and every matching `_service._tcp` value to the app target, not package/framework metadata.
- Add permission denial and Settings-recovery UI; do not equate unavailable discovery with no peers.

### Phase 4: opt in securely

- Initialize explicitly with `backend: .networkFramework`.
- Use `networkSecurity: .preSharedKey(secret)` for sensitive sessions.
- Require at least 32 CSPRNG-generated bytes from authenticated provisioning and protected storage.
- Never put keys in source, bundles, arguments, logs, screenshots, discovery metadata, or invitation context.
- Treat TLS-PSK as shared-group membership only. Never authorize by `Peer.displayName` or a self-asserted identifier.

### Phase 5: adapt behavior and UI

- Keep `.automatic` only where automatic connection is intended.
- For user-selected outbound connections, use `.custom`, `PeerBrowserModel`, app-owned UI, and `invitePeer`.
- Own permission/error, empty, selection, progress, cancellation, accessibility, and lifecycle states.
- Treat Network invitation context and caller timeout as ignored.
- Do not claim app-owned outbound selection supplies inbound approval.
- Replace stream/resource use with bounded `Data`/`PeerMessage`, or retain MC for that session.

### Phase 6: verify and roll out

- Run focused automated checks for modified app behavior.
- Exercise two physical devices across permission, topology, security, lifecycle, and reconnect cases.
- Record device/OS/topology/backend/security/app-protocol evidence without secrets.
- Roll out to coordinated cohorts and compare agreed success metrics.
- Roll back all communicating peers to MC when thresholds are crossed.

## Guardrails

- Never claim MC and Network have direct wire interoperability; there is no bridge or relay.
- Never change the library backend default as part of an adopting-app migration.
- Never silently fall back from failed Network security to plaintext or MC.
- Never present `.unauthenticated` plaintext TCP as production security.
- Never claim TLS-PSK authenticates an individual peer.
- Never use discovery or invitation metadata for secrets or trust decisions.
- Never imply `includePeerToPeer` guarantees Bluetooth, AWDL, an interface, or connectivity.
- Never treat simulator/loopback success as physical-device validation.
- Never hide unsupported stream/resource or invitation behavior behind changed semantics.
- Do not modify `AGENTS.md` or `CLAUDE.md` unless explicitly requested.

## Repository build and test commands

Use the exact repository commands from `AGENTS.md` when library code or project configuration changes:

```bash
# Build the framework (iOS Simulator)
xcodebuild -workspace PeerConnectivity.xcworkspace \
  -scheme PeerConnectivity \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -configuration Debug build

# Build via Swift Package Manager
swift build
```

```bash
# Run all tests
xcodebuild test -workspace PeerConnectivity.xcworkspace \
  -scheme PeerConnectivity \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -configuration Debug

# Run a single test class
xcodebuild test -workspace PeerConnectivity.xcworkspace \
  -scheme PeerConnectivity \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -only-testing:PeerConnectivityTests/PeerMessageTests

# Run a single test method
xcodebuild test -workspace PeerConnectivity.xcworkspace \
  -scheme PeerConnectivity \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -only-testing:PeerConnectivityTests/PeerMessageTests/testSimpleMessageRoundTrip
```

For documentation-only changes, validate links/frontmatter and run `git diff --check`; tests are not required.

## Verification checklist

- [ ] Network remains explicit opt-in and MC remains fallback/default.
- [ ] Deployment targets and unsupported-OS behavior are understood.
- [ ] Every service type is valid and declared as `_service._tcp` in the app target.
- [ ] Local Network allow, deny, and recovery UX is verified.
- [ ] PSK generation, provisioning, storage, rotation, mismatch, and non-leakage are verified.
- [ ] No authorization or audit decision trusts display name/identifier alone.
- [ ] Browser, invitation, context, timeout, and inbound approval differences are explicit.
- [ ] Stream/resource and MC-specific API dependencies are removed or retained on MC.
- [ ] Mixed app versions use the same backend and compatible app protocol.
- [ ] Physical-device topology, lifecycle, bidirectional messaging, and reconnect evidence is recorded.
- [ ] Metrics contain no secrets and rollback thresholds/owner are documented.
- [ ] Internal documentation links, skill frontmatter, and `git diff --check` pass.
